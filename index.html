AIAnalyzer: A Static Analysis Tool That Knows When to Ask AI for Help
Swift · CLI · Static Analysis · AI
The Problem

Over 18 years of iOS work, I kept hitting the same wall: messy, hard-to-maintain Swift codebases with no good tooling to catch architectural rot early. Most static analysis tools for Swift are either too generic (linting style, not architecture) or don't exist at all for the specific smells that actually sink a codebase over time — God Objects, oversized classes, tangled responsibilities.

At the same time, I wanted to go deeper on something I'd started exploring in an earlier project: combining on-device AI with cloud AI in a single system that intelligently chooses between them, rather than picking one or the other.

The Approach

AIAnalyzer is a Swift CLI that parses codebases with SwiftSyntax, detects architectural smells (God Objects, Large Classes, High Method Density), and — the part I'm most proud of — offers AI-powered fix suggestions through four provider modes:

  • Gemini (Cloud) — best quality, requires network + API key
  • Ollama (Local LLM) — a full local language model running via Ollama, fully on-device, no data leaves the machine
  • Local (Core ML) — a lighter-weight on-device option with its own heuristic fallback, useful when a full Ollama-hosted model isn't available
  • Hybrid — attempts a local-preferred provider first, evaluates confidence based on output quality, and automatically escalates to Gemini only when the local result looks weak

That fallback logic is the core engineering problem I wanted to solve: not "which AI should I use," but "how does the system know, in real time, whether its own answer is good enough to trust."

Eating My Own Dog Food

Once the core tool worked, I turned it on itself — and found the irony immediately: AnalyzerApp.swift, the app's own entry point, was a 695-line God Object, the exact smell the tool exists to catch. I used that as the starting point for a full self-audit: migrating CLI parsing to Apple's swift-argument-parser, decomposing the God Object into focused components, fixing a real false-positive bug in the classification logic (the tool was misreading class names like DetailViewControllerDelegate as ViewControllers), and automating the entire release pipeline — tagging a version now builds, tests, and publishes to Homebrew with zero manual steps.

Outcome
  • Fully automated CI/CD: 59 passing tests, automated Homebrew formula updates, SARIF output for GitHub code scanning integration
  • A working, publicly installable tool (brew install elangbamjohnson/tap/aianalyzer), not just a demo
  • A real answer to a real architecture question: how to build AI systems that make trustworthy decisions about when to rely on lighter local inference versus escalating to a stronger cloud model — directly relevant to teams building cost-conscious or privacy-sensitive AI features
